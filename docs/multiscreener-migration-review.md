## 用户已确认的适配

- 加载截至筛选日的全部本地历史，替代原入口750自然日。策略内部窗口与参数原样保留。这是明确批准的输入范围变化，可能使原来历史不足的策略开始工作。
- 公共 StrategyResult 增加可选 timeframe，修复周/月均线回调触发信号时的接口不匹配。七个策略文件没有任何算法修改。
- 使用通达信前复权价格，锚点截至筛选日；数据库成交量仍为股，进入旧策略时除以100转换为手，金额仍为元。
- 先接技术选股；基本面明确标记 `not_connected`，不以零值或通过标志代替。
- 从日线按旧聚合规则重建周月线，每周期一根，当前周期一根动态K线；不复制旧数据库可能遗留的多条动态记录。

公共基类仅将不再使用的旧ORM会话类型注解适配为 Any，并补齐 timeframe 字段。策略实际不访问旧ORM会话。运行参数固定为原默认配置，不趁移植修复旧入口非空参数的嵌套传递差异。

## 保留的执行规则

默认顺序：日均线回调、多级别一阳穿四线、日突破、周均线回调、月均线回调、周突破、月突破。

逐股、逐策略独立执行，仅汇总 `signal_date == effective_date` 且 `signal_type != NO_SIGNAL` 的信号，不取策略交集、不按评分或基本面再过滤。每个信号独立一行。单策略异常继续扫描其他策略，但明确展示错误。

源码中的比较符、舍入、滚动均线的 min_periods、分型、笔、峰值资格与失效规则均保留。原多级别交叉策略自行执行 W-FRI / ME 重采样；未将其替换为公共聚合器。因此它的周月信号仍受原周期日期和当日信号过滤规则约束。

公共输入聚合保留历史周 W-FRI、历史月 BME（工作日月末）标签，当前动态周期标筛选日，OHLC分别首/最高/最低/末值，量、金额、换手率按原代码求和。不能用看盘图“最后实际交易日”的标签替代这些策略输入。

原 signal_level 的策略名映射保持，交叉策略的实际级别也保留在 details.level，未顺手更正其旧输出分类。

## 独立接入

网页新增“多策略选股”；原“技术选股”与 `/api/screens`、`technical_screen` MCP 工具保持。

网页新选股统一自动使用数据库最新可用盘后交易日，日期只读，不提交历史as_of；服务端在每次提交时重新按原盘后数据覆盖规则选取日期，不依赖浏览器预览或上次任务日期。盘后时点及至少80%相对覆盖规则保留，少量个股先更新不自动推进全市场日期。API显式as_of仍保留给历史研究，网页不提供历史入口。行情、事件与股本均不读取技术截止日之后的记录；历史成分股仅覆盖已采集的快照，结果附加财务参考见后文。

GET /api/multi-screens/latest返回当前最新选股日期及覆盖情况。旧结果独立保留并标注旧日期，不能改成最新日期冒充重算。默认最新任务仍运行时，若数据库已有新交易日，新提交不会复用旧任务，提示先等待或停止；自动最新任务在日期变化后拒绝继续，需新建最新日期任务，避免混合两日逐股结果。网页也禁用日期不同的旧任务继续按钮。

网页“运行原多策略选股”现在先提交持久化行情准备任务：逐文件核对本地交易日期、文件大小、修改时间戳及尾部指纹，新增或变化文件复用原增量导入，再次扫描确认没有待同步文件，按本地与数据库盘后覆盖规则确认最新可用日一致，最后创建该日期的技术选股任务。相同日期但内容修订也会入库；权息gbbq指纹变化同样触发同步。原完整哈希校验入口仍可检查保留时间戳的早期历史修订。

“更新通达信行情”走相同核对与同步流程，但不创建技术任务。财务与股本专业快照仍由独立更新入口维护。准备状态、前后日期、缺文件数量、导入任务及选股任务关联保存在market_prepare_run；页面轮询显示文件进度及新增修订行，刷新后恢复运行中的准备任务。重复请求复用相同参数的运行任务；不同参数拒绝叠加。服务中断后重新提交会识别无主准备任务并复用逐文件已入库内容，不静默重新启动技术选股。

文件写入中、源文件核对失败、导入部分失败、同步后源文件再次变化或最新可用日未对齐时，准备任务失败且不启动技术选股。长期缺少的源文件、较旧文件显式计数并保留原数据，不用旧文件回退数据库，也不假称全量覆盖。只有少数IPO更新的日期不会当成全市场最新盘后日。正在运行技术选股时拒绝启动网页准备任务，以免用户在一次扫描中主动切换行情。

接口：POST /api/market-prepare，空对象仅更新行情，传screen（原MultiScreenRequest且as_of为空）表示同步后新建选股；GET同地址查看最近准备任务，GET /api/market-prepare/{id}查看指定任务及其import_progress。原POST /api/multi-screens和MCP直接启动接口保留原任务ID契约，面向已完成同步或显式历史研究，不替调用者自动下载通达信数据。

后台任务、逐股结果独立保存在 multi_screen_run / multi_screen_item。进度和结果持续保存，支持停止、重复提交复用；服务异常退出后，新提交会识别无主任务并标中断。默认最多4进程按股票并行，可选1/2/4。每个进程独立读取数据并创建策略实例，主进程写数据库；按原股票及策略顺序读取结果，完成顺序不参与排序。停止后不再派发新股票，已在处理的最多4只处理完并保存，随后停止。

停止、中断或失败任务可继续未完成部分。保持原任务ID、截止日、所选策略和已保存逐股结果，仅为尚未保存结果的股票派发计算。保留已有错误，不因继续而自动重算失败股票。已完成结果保持原样；未处理部分仍读取继续运行时数据库中截至原筛选日的数据，任务并未冻结整份行情快照。股票池数量或已有成分不一致时拒绝继续，提示新建任务。

截至筛选日无数据、暂不支持的复权事件和执行异常均明确展示；历史覆盖列展示日周月根数。初始历史检查提示仅诊断，不参与筛选或替代策略判断。有效执行无信号时返回空列表，不补造候选。

## 使用

刷新本地网页 → 多策略选股 → 选择策略及股票范围 → 运行。股票留空表示全所选池，支持代码、完整名称及逗号/空格分隔。可展开原默认参数、数据与执行问题、历史覆盖，最近任务可以重新打开。

- `GET /api/multi-screens/strategies`：原策略清单与实际默认参数。
- `POST /api/multi-screens`：as_of、symbols（完整证券代码）、taxonomy_id、strategies（类名列表）、workers（1至4，默认4），返回任务id。
- `GET /api/multi-screens/{id}`：进度、全部信号、错误与覆盖。
- `POST /api/multi-screens/{id}/cancel`：请求停止。
- `POST /api/multi-screens/{id}/resume`：workers（默认4），保留已存逐股结果并继续剩余股票。
- MCP：multi_strategy_catalog、start_multi_screen、multi_screen_status。

未来新增策略在独立模块实现后登记 REGISTRY，不改现有七个文件；新增策略需独立验证后才加入默认清单。
